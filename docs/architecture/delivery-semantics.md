# Семантика доставки

Что Telemax обещает про сообщение и что не обещает. Документ описывает
**реализованное поведение**, не намерения.

## Главное обещание

> Сообщение не исчезает молча.

В любой момент времени сообщение находится ровно в одном из состояний, и
каждое из них **видно владельцу** в `/status` у бота-стража:

* доставлено;
* ждёт повтора;
* явно помечено `failed`;
* явно помечено `ambiguous` (отправлено, подтверждение потеряно).

Чего Telemax **не обещает**: exactly-once. Ниже честно перечислено, где
возможен дубль.

## Состояния задачи доставки

```
RECEIVED ──► PENDING ──► LEASED ──► DELIVERED
                │           │
                │           ├──► RETRY_WAIT ──► PENDING
                │           ├──► AMBIGUOUS
                │           └──► FAILED
                └──► EXPIRED (TTL вышел, не отправлено)
```

| Состояние | Значение | Кто ставит |
|---|---|---|
| `RECEIVED` | Событие durable-зафиксировано на входе. Ещё не решено, куда его слать. | intake |
| `PENDING` | Задача создана, ждёт воркера. | intake / retry |
| `LEASED` | Воркер взял задачу, lease действует до `lease_expires_at`. | воркер |
| `DELIVERED` | Удалённый API **подтвердил** приём и вернул id сообщения. | воркер |
| `RETRY_WAIT` | Повторяемая ошибка, ждём `next_attempt_at`. | воркер |
| `AMBIGUOUS` | Отправка ушла, подтверждение не получено. Дубль возможен при ручном повторе. | воркер |
| `FAILED` | Постоянная ошибка или исчерпаны попытки. | воркер |
| `EXPIRED` | TTL истёк раньше, чем удалось отправить. | воркер |
| `ARCHIVED` | Владелец прочитал отказ и убрал его. Строка, ошибка, попытки и время сохраняются; из счётчика и инцидента выходит. | владелец |

Ключевое правило: **строка mapping не означает доставку**. Доставка — это
`DELIVERED`, и только после подтверждённого remote message id.

## Что защищено от дублей и где дубль возможен

| Направление | Тип | Дедуп на входе | Возможен дубль? |
|---|---|---|---|
| MAX → Telegram | текст | `UNIQUE(max_chat_id, max_message_id, telegram_bot_id)` | **Редко**: только при ручном retry из `AMBIGUOUS`. |
| MAX → Telegram | **медиа и альбомы** | там же | **Редко**, там же. |
| Telegram → MAX | текст | `UNIQUE(bot_id, update_id)` в `telegram_inbox` | **Редко**, там же. |
| Telegram → MAX | медиа и альбомы | там же | **Редко**, там же. |

**Все четыре пути идут через одну очередь.** Текст и вложения
используют одинаковую durable-схему: событие сначала фиксируется,
после чего отдельный воркер выполняет отправку.

### Что лежит в job'е медиа

Байтов нет и ссылки нет. MAX выдаёт ссылки с истечением, поэтому хранить их
как единственный источник — значит гарантировать провал повтора. Хранится
`raw` вложения (`videoId` / `audioId` / `fileId` / `token`) плюс id чата и
сообщения; свежий URL резолвится **на каждой попытке**. Превью в байтах
выбрасывается: это контент, и в базе ему не место.

Одно MAX-сообщение — одна job'а, сколько бы вложений в нём ни было. Альбом
целиком либо уходит, либо остаётся в очереди; половина альбома не доставляется.

Повтор события источником дубля **не создаёт**: и MAX-событие, и Telegram
update идемпотентны по своему UNIQUE-ключу.

## Окно неоднозначности

Оно существует, и спрятать его нельзя:

```
воркер вызывает send() ──► удалённый API принял сообщение
                              │
                              ▼
                    процесс умирает здесь
                              │
                              ▼
              remote message id не записан в SQLite
```

После рестарта задача выглядит как «отправка начиналась, результат неизвестен».

Как это различается: **непосредственно перед** обращением к удалённому API
job'а получает отметку `send_started_at`. Если lease истёк, а отметки нет —
отправка не начиналась, задача просто повторяется. Если отметка есть —
результат неизвестен, и job уходит в `AMBIGUOUS`.

Отметку ставит сам отправитель, а не очередь: для медиа MAX → Telegram она
навешена на сендер внутри `MaxMediaDelivery`, поэтому резолв ссылки,
скачивание и валидация проходят **до** неё, а срабатывает она ровно один раз
на сообщение — даже если это альбом из нескольких файлов.

Проверено вживую убийством процесса в обоих окнах:

| Момент падения | Результат | Дубль |
|---|---|---|
| во время скачивания медиа | `done` после рестарта | нет, 1 копия |
| после первого обращения к Telegram | `ambiguous` | нет, повтора не было |

Что делает Telemax:

1. **Не отправляет повторно автоматически.** Автоповтор в этом окне —
   это генератор дублей у родственника в чате.
2. Ставит `AMBIGUOUS` и показывает в `/status` отдельной строкой.
3. Даёт владельцу решение: повторить или пометить решённым.

Telegram Bot API не даёт универсального idempotency key — это факт протокола,
а не недоработка. Для MAX `cid` (client-generated id) в перспективе позволяет
сузить окно; на текущем HEAD это research item, а не реализованная защита.

## Порядок сообщений

Гарантируется **внутри одного моста**: сообщения одного контакта уходят в том
порядке, в котором пришли.

Между мостами порядка нет и он не нужен: у «Папы» и «Мамы» отдельные очереди,
и застрявшая очередь одного не задерживает другого.

Тяжёлая работа (скачивание медиа) может идти параллельно; последовательным
остаётся финальный `send` внутри одного чата.

## Ограничения повторов

| Параметр | Значение | Почему |
|---|---|---|
| Максимум попыток | см. `retry/backoff.py` | Бесконечный повтор — это очередь, которая никогда не сходится. |
| Backoff | экспоненциальный + jitter | Джиттер разводит мосты, проснувшиеся после общего сбоя сети. |
| `Retry-After` | уважается дословно | Сервер назвал точное время — своя догадка тут только вредит. |
| Lease | истекает по времени | Задача, зависшая в `LEASED` после падения, возвращается в работу. |
| TTL | ограничен | Сообщение недельной давности доставлять уже незачем. |

## Хранение payload и приватность

Компромисс сформулирован явно: **durable retry требует хранить содержимое
сообщения на диске**, иначе повторять нечего.

Что делается для сужения этого:

* тяжёлые файлы в SQLite **не хранятся** — хранится ссылка
  (Telegram `file_id`, MAX media id) и файл перекачивается при повторе;
* после `DELIVERED` payload вычищается, остаются mapping и метаданные;
* токены и секреты в БД не попадают никогда — только **имя** env-переменной;
* база лежит в каталоге с ограниченными правами, рядом с MAX-сессией.

## Восстановление после падения

При старте процесс:

1. применяет миграции (атомарно, см. ADR);
2. возвращает просроченные `LEASED` в `PENDING`;
3. поднимает необработанные записи `telegram_inbox` и доводит их до MAX;
4. восстанавливает незавершённые media groups;
5. запускает воркеры по мостам.

Ничего из этого не требует участия владельца.

## Ручные действия владельца

Через бота-стража:

* `/status` — очереди, ошибки, ambiguous, возраст старейшей задачи;
* `/failed`, `/ambiguous`, `/archived` — списки;
* `/retry НОМЕР` — повторить;
* `/resolved НОМЕР` — «проверил, дошло»;
* `/archive НОМЕР причина` — убрать неисправимое, **не удаляя историю**.

Архив — не удаление. Строка остаётся с исходной ошибкой, числом попыток и
временем; к ней дописывается причина архивации. Смысл в том, чтобы
безнадёжная задача перестала держать инцидент открытым и маскировать
следующий настоящий отказ.

### Никакого пути мимо очереди

Медиа MAX → Telegram отправляется **только** из сендера очереди. Раньше это
нарушалось дважды: исходной веткой `on_max_message` и «страховочным»
fallback'ом в `except UnstorablePayloadError`, который отправлял напрямую
именно тогда, когда durable-запись не удалась. Оба убраны.

Если payload невозможно сохранить даже после санитайза — job всё равно
создаётся и сразу помечается `FAILED` с причиной. Сообщение не доставлено и
не потеряно: оно в списке `/failed`.

Инвариант держит `tests/test_no_media_bypass.py` — он читает исходники и
падает, если `deliver()` вызовут вне разрешённых мест или снова из
`except`-блока.

## Резервное копирование

Терять здесь можно две вещи: **SQLite-базу** (mapping и очереди) и
**MAX-сессию** (авторизация). Обе лежат в `data_dir`. Резерв — обычная
копия каталога при остановленном сервисе; на ходу для базы —
`sqlite3 .backup`, потому что WAL нельзя копировать простым `cp`.
