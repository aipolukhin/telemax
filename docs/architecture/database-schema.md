# Схема базы данных

Один файл SQLite в `data_dir`, режим WAL, миграции версиями в коде
(`bridge/storage/migrations.py`). Текущая версия — **10**.

Весь SQL проекта живёт в `bridge/storage/repositories.py` и в миграциях.
Больше нигде запросов нет — это то, что делает утверждения вроде «токенов в
базе нет» проверяемыми тестом, а не обещанием.

## Правило про секреты

**В базе не хранится ни одного токена.** Хранится только *имя* переменной
окружения (`bridges.token_env`). Проверяется тестом
`test_schema_holds_no_token_columns`.

## Таблицы доставки

### `message_map` — соответствие сообщений

Кто чему соответствует в обе стороны. Строка появляется **до** отправки,
потому что MAX возвращает наше же сообщение эхом, и без записи в карте это эхо
уедет владельцу как сообщение от контакта.

| Колонка | Смысл |
|---|---|
| `max_chat_id`, `max_message_id` | сторона MAX |
| `telegram_bot_id`, `telegram_chat_id`, `telegram_message_id` | сторона Telegram |
| `telegram_owner_message_id` | id в нумерации *владельца* — для сообщений, размещённых от его имени (V7) |
| `direction`, `source_marker` | кто автор; основа loop guard |

Индексы: `UNIQUE(max_chat_id, max_message_id, telegram_bot_id)` — дедуп
MAX → Telegram; `UNIQUE(telegram_bot_id, telegram_message_id)` — обратно. Оба
частичные, чтобы строки без id не конфликтовали между собой.

> **Наличие строки не означает доставку.** Оно означает, что попытка была.
> Доставку означает `outbox.state = done` с проставленным `remote_message_id`.

### `outbox` — очередь доставки

Одна логическая очередь на мост.

| Колонка | Смысл |
|---|---|
| `state` | `pending` / `inflight` (= leased) / `done` / `failed` / `ambiguous` / `expired` / `archived` |
| `attempts`, `next_attempt_at` | backoff |
| `lease_expires_at` | до какого момента задачу держит воркер (V8) |
| `expires_at` | TTL: после него доставлять уже незачем (V8) |
| `source_key` | ключ исходного события; `UNIQUE` — повтор события не создаёт вторую задачу (V8) |
| `remote_message_id` | что вернул удалённый API; **только с ним доставка считается подтверждённой** (V8) |
| `send_started_at` | момент **непосредственно перед** обращением к удалённому API (V9); ставит сам отправитель. Отличает «не отправляли» от «отправили, результат неизвестен» при истёкшем lease |
| `ambiguous_at` | когда отправка ушла без подтверждения (V8) |
| `payload_json` | что отправлять; **вычищается после `done`** |

### `telegram_inbox` — durable intake (V8)

Update Telegram ложится сюда **до** того, как его offset подтверждён серверу.
Это единственное, что отделяет «процесс упал» от «сообщение исчезло».

`UNIQUE(bot_id, update_id)` — повтор после рестарта становится no-op.
`payload_json` вычищается после обработки.

### `telegram_offset` — курсор опроса (V8)

`next_offset` на бота, чтобы рестарт не перечитывал сутки истории. На
корректность не влияет — от дублей защищает уникальный индекс выше.

### `media_group_part` — части альбома (V8)

Альбом приходит несколькими updates без признака последнего, поэтому части
хранятся по отдельности и группа пересобирается после рестарта.
`UNIQUE(media_group_id, telegram_message_id)`.

Заменила `pending_media_group` из V1 — та была создана и **никогда не
использовалась ни одной строкой кода**; V8 её удаляет.

### `health_state` — что переживает процесс (V10)

Несколько скаляров, не хранилище метрик: когда процесс стартовал, когда MAX
подключился и отвалился, сколько было переподключений, был ли прошлый выход
штатным. Всё считаемое — глубина очередей, возраст старейшей задачи — считается
в момент запроса из таблиц, которые это и так держат.

Ключ `running` ставится на старте и снимается при штатной остановке: найти его
поднятым — значит прошлый процесс убили.

### `alert_outbox` и `alert_incidents` — уведомления владельцу (V10)

`alert_outbox` — очередь сообщений в чат стража, с повторами: сбой, о котором
уведомляют, часто и есть тот сбой, который уведомление проглотит.

`alert_incidents` — память о том, что проблема уже известна. Инцидент
открывается один раз, о нём сообщают один раз, закрывают один раз. Очередь в
сорок задач — это одно уведомление, а не сорок.

В тексте уведомления нет содержимого переписки, номеров, токенов и ссылок:
только сколько и как давно.

## Миграции

Шаг = одна транзакция: `BEGIN IMMEDIATE` → все statements → запись
`schema_version` → `COMMIT`. Любое исключение — `ROLLBACK`.

Это приходится делать явно: драйвер SQLite в Python по умолчанию выполняет DDL
**вне** транзакции, из-за чего до версии 8 шаг, упавший на середине, оставлял
часть таблиц созданными с неизменной `schema_version`, и следующий старт падал
на «table already exists» **навсегда**. Доказано экспериментом, закрыто тестами
в `tests/test_migrations_atomic.py`.

`archived` добавлено без миграции: колонка `state` — TEXT без CHECK-констрейнта,
проверено по боевой схеме перед изменением.

Правила добавления шага:

* **дописывать, никогда не править существующий** — чья-то база его уже прошла;
* не добавлять колонку с секретом;
* помнить, что `ALTER TABLE ... DROP COLUMN` в SQLite не работает, если на
  колонке висит индекс.

## Резервное копирование

Терять здесь можно две вещи: **базу** (карта сообщений и очереди) и
**MAX-сессию** (авторизация). Обе в `data_dir`.

При остановленном сервисе — обычная копия каталога. На ходу база копируется
**только** через `sqlite3 data/bridge.db ".backup data/backup.db"`: в режиме WAL
простой `cp` даёт битый файл.
