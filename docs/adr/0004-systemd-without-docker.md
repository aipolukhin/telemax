# ADR 0004 — systemd как супервизор, без Docker

Статус: принято.

## Контекст

Приложение должно переживать падения и подниматься при старте машины.
Нужен супервизор.

## Решение

Внешний супервизор — **systemd**. Внутри процесса второго супервизора
уровня PID1 не строится.

Деплой: обычный Python, venv, SQLite, systemd-юнит.

## Почему не Docker

* один личный процесс на своей машине — оркестрация решает задачу, которой
  здесь нет;
* MAX-сессия и SQLite-база должны переживать пересборку образа, то есть всё
  равно выносятся в volume;
* образ добавляет слой между владельцем и логами ровно в тот момент, когда
  что-то сломалось;
* обновление `git pull && systemctl restart` короче любого docker-цикла.

## Требования к юниту

```ini
Restart=on-failure
RestartSec=<пауза, чтобы не крутить рестарт-петлю>
TimeoutStopSec=<больше, чем drain очередей>
NoNewPrivileges=yes
PrivateTmp=yes
User=<отдельный пользователь, не root>
```

`TimeoutStopSec` обязан превышать время слива очередей: если systemd пришлёт
SIGKILL раньше, чем процесс дописал принятые сообщения, вся durable-механика
из ADR 0001 обесценится на последнем шаге.

## Что обязан делать процесс по SIGTERM/SIGINT

По порядку:

1. остановить polling — новые updates не принимаются;
2. durable сохранить всё, что уже принято;
3. дождаться критических транзакций;
4. освободить lease (или дать им истечь — воркер после рестарта разберётся);
5. закрыть Telegram-сессии;
6. закрыть PyMax;
7. закрыть SQLite.

Порядок не косметический: закрыть базу раньше, чем дописаны принятые
сообщения, — это ровно та потеря, от которой всё строилось.

## Последствия

* `systemctl status`, `journalctl -u` работают как ожидается;
* нет изоляции контейнера — компенсируется отдельным пользователем,
  `NoNewPrivileges`, `PrivateTmp` и правами на каталоги;
* переносимость на не-systemd системы теряется. Для личного сервера
  приемлемо.
