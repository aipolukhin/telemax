# ADR 0002 — At-least-once и явное состояние AMBIGUOUS

Статус: принято.

## Контекст

Между «удалённый API принял сообщение» и «мы записали это в SQLite» есть
окно. Если процесс умирает внутри него, результат отправки неизвестен
принципиально.

Telegram Bot API **не даёт idempotency key**: нельзя сказать «отправь это
сообщение, но если ты его уже принял — не создавай второе». Это свойство
протокола.

Значит выбор ровно из двух вариантов, третьего нет:

* повторить и иногда сделать дубль;
* не повторить и иногда потерять.

## Решение

Telemax реализует **at-least-once с явной пометкой неопределённости**, а не
exactly-once.

1. Задача, упавшая **до** отправки, повторяется — потери нет, дубля нет.
2. Задача, упавшая **в окне подтверждения**, получает `AMBIGUOUS`
   и **не повторяется автоматически**.
3. `AMBIGUOUS` видно владельцу в `/status` отдельной строкой.
4. Владелец решает сам: повторить или пометить решённым.

Слово exactly-once в документации не употребляется. Оно было бы неправдой.

## Почему не автоповтор ambiguous

Родственник в чате видит результат каждой догадки. Автоповтор при массовом
сбое сети превращается в пачку дублей у живого человека — цена ошибки
несимметрична, и решать должен владелец, у которого есть контекст.

## Почему не отказ от повтора вовсе

Это возврат к тихой потере, ради которой всё и переделывалось.

## Последствия

* владелец получает честную картину вместо ложного «доставлено»;
* появляется ручное действие, которое иногда придётся делать;
* дубль возможен только как **осознанный выбор владельца**, никогда сам по себе.

## Направление сужения окна

Для MAX существует `cid` — client-generated id, который сервер возвращает в
эхе. Он в принципе позволяет после рестарта спросить «моё сообщение с этим
`cid` дошло?» и превратить `AMBIGUOUS` в определённый ответ.

На текущем HEAD это **research item, а не реализованная защита**, и в
документации оно так и описано. Для Telegram аналога нет; частичная
реконсиляция возможна только через mapping.
