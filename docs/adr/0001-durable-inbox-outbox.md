# ADR 0001 — Durable inbox и outbox на пути доставки

Статус: принято.

## Контекст

Ранняя реализация уже содержала:

* полноценный `OutboxRepository` со схемой, состояниями и `requeue_inflight()`;
* работающий `OutboxWorker` с классификацией ошибок и backoff;
* `WorkerPool` с изоляцией очередей по мостам;
* тесты, покрывающие всё перечисленное.

И ни одного вызова `enqueue()` из `bridge/`. Доставка шла напрямую из
`BridgeRouter`, а вся очередь работала только в тестах.

Дедуп при этом писался **до** отправки. В связке с прямой отправкой это даёт
не защиту, а механизм потери: строка в `message_map` существует, отправка
упала, повтор события от MAX видит строку и считает сообщение доставленным.

## Решение

Регистрация источника и создание задачи доставки происходят **в одной
транзакции**. Отправка выполняется отдельным воркером из очереди.

```
событие ──┬─ (одна транзакция) ─┬─ запись источника (UNIQUE)
          │                     └─ создание job PENDING
          │
          └─ воркер ── LEASED ── send() ── DELIVERED (после remote id)
```

Для Telegram добавляется `telegram_inbox` с `UNIQUE(bot_id, update_id)`:
update сохраняется durable **до** сдвига offset.

Успех фиксируется только после того, как удалённый API вернул id сообщения.
Адаптер, вернувший `None`, успехом не считается.

## Последствия

Хорошее:

* падение сети, Telegram, MAX или процесса больше не теряет сообщение;
* повтор события источником не создаёт вторую задачу;
* очередь одного контакта не блокирует другого;
* `/status` показывает правду, а не «доставлено» для несуществующего сообщения.

Цена, принимаемая осознанно:

* **содержимое сообщения лежит на диске** до подтверждения доставки. Без
  этого повторять нечего. После `DELIVERED` payload вычищается;
* доставка получает лишний round-trip в SQLite. На масштабе «до 10 близких
  контактов» это неизмеримо;
* появляется состояние `AMBIGUOUS`, которого раньше не было. Это не
  усложнение ради усложнения — окно существовало и раньше, просто
  заканчивалось тихой потерей вместо явной пометки.

## Отвергнутые варианты

**Оставить прямую отправку, добавить повтор в памяти.** Не переживает
рестарт — то есть не решает ровно ту задачу, ради которой затевалось.

**Писать дедуп после отправки.** Меняет потерю на дубль: MAX переподключается
и повторяет событие, копия уходит владельцу второй раз. Для личной переписки
дубль лучше потери, но обе беды лечатся одной транзакцией.

**Взять готовую очередь (Celery, arq, dramatiq).** Требует Redis. Ограничения
проекта — venv, SQLite, systemd, никакого Docker. SQLite как очередь на этом
масштабе полностью достаточен.
