# Runbook: что делать, когда что-то пошло не так

Для владельца и для того, кто чинит. Сначала — как понять, что происходит,
потом — как чинить.

---

## Вас уведомят сами

Не нужно постоянно проверять `/status`: Страж сам пишет о проблеме,
один раз на инцидент:

* MAX недоступен дольше 10 минут — и отдельно, когда связь вернулась;
* появились недоставленные сообщения;
* появились отправки с неясным результатом;
* очередь выросла или перестала двигаться.

Одна проблема — одно сообщение, не одно на каждую повторную попытку. Содержимого
переписки в уведомлениях нет: только сколько и как давно.

Команды для разбора:

| Команда | Что делает |
|---|---|
| `/failed` | что не доставлено и почему |
| `/ambiguous` | что могло не дойти — проверьте в MAX глазами |
| `/retry НОМЕР` | поставить задачу в очередь заново |
| `/resolved НОМЕР` | «я проверил, дошло» — закрыть неясную |
| `/archive НОМЕР причина` | убрать неисправимую, сохранив историю |
| `/archived` | что лежит в архиве |

## Первое, что смотреть

`/status` у бота-стража. Он показывает:

| Строка | Что значит |
|---|---|
| `MAX: подключён / нет связи` | жива ли пользовательская сессия MAX |
| `Очередь: N` | сколько сообщений ждут отправки |
| `Принято, не отправлено: N` | updates легли на диск, но ещё не унесены |
| `Самое старое в очереди: N мин` | если растёт — что-то стоит |
| `Не доставлено: N — нужен повтор` | постоянные отказы, ждут решения |
| `Неясный результат: N — проверьте в MAX` | отправка ушла, подтверждения нет |
| `Аптайм` / `MAX офлайн` / `Переподкл.` | из persistent-снимка: переживает рестарт |
| `Прошлый запуск был после аварийного завершения` | предыдущий процесс убили, а не остановили |
| `Не работает: имена` | фоновая задача умерла |

Из терминала:

```bash
systemctl status telemax
journalctl -u telemax -n 200 --no-pager
```

## «Сообщение не дошло»

Оно **не исчезает молча** — это главное свойство, ради которого всё
переделывалось. Значит оно в одном из состояний:

```bash
sqlite3 data/bridge.db \
  "SELECT id, bridge_name, kind, state, attempts, last_error
     FROM outbox WHERE state NOT IN ('done') ORDER BY id;"
```

| Состояние | Что делать |
|---|---|
| `pending` | ничего, воркер заберёт; смотреть `next_attempt_at` |
| `inflight` | занято воркером; если `lease_expires_at` в прошлом — вернётся само в течение 30 с |
| `failed` | постоянный отказ. Прочитать `last_error`, починить причину, повторить вручную |
| `ambiguous` | **проверить в MAX глазами.** Дошло — `/resolved`; не дошло — `/retry`. Сюда попадает только падение **после** начала отправки: падение во время скачивания медиа повторяется само |
| `archived` | владелец убрал это в сторону. Действий не требует, история сохранена |
| `expired` | вышел TTL. Отправлять заново уже бессмысленно, сказать владельцу |

Про `ambiguous` подробно — `docs/architecture/delivery-semantics.md`.
Коротко: отправка ушла, ответ потерялся, и автоповтор здесь создаёт дубли
у живого человека. Решает владелец.

## «Мост стоит, очередь растёт»

Порядок сообщений внутри одного моста сохраняется, поэтому **застрявшая
голова очереди держит всё за собой**. Это сделано намеренно: иначе контакт
прочитает переписку не в том порядке.

Найти голову:

```bash
sqlite3 data/bridge.db \
  "SELECT id, state, attempts, last_error FROM outbox
    WHERE bridge_name='dad' AND state IN ('pending','inflight')
    ORDER BY id LIMIT 1;"
```

Если она безнадёжна — пометить `failed`, и очередь пойдёт дальше. Задача
останется видимой в `/status`.

Другие мосты при этом работают: очереди изолированы по мосту.

---

## «MAX отвалился»

Watchdog поднимает сессию сам раз в минуту. Если не помогает:

* MAX разлогинил устройство → нужна повторная авторизация через стража;
* сессия побилась → `data/max-session/`, восстановление из резерва;
* `Bot has restriction to input [chat.control]` → служебный аккаунт, писать
  туда нельзя. Это постоянный отказ, не сетевая проблема.

Telegram при отсутствии MAX **продолжает принимать** сообщения: они лягут в
очередь и уйдут, когда связь вернётся. Это правильное поведение, а не потеря.

## «Процесс не поднимается»

```bash
journalctl -u telemax -n 100 --no-pager | grep -i -A5 traceback
```

Частые причины:

| Симптом | Причина | Что делать |
|---|---|---|
| `$TELEMAX_...` is not set | нет токена в env | проверить файл секретов и его права |
| `is not a valid bot token` | токен отозван | пересоздать бота у стража |
| ошибка миграции | шаг упал | **база цела**: шаг откатывается целиком. Прочитать ошибку, чинить причину |
| `database is locked` | второй процесс на той же базе | найти и остановить: `fuser data/bridge.db` |

Про миграции: начиная с версии 8 упавший шаг откатывается полностью и
`schema_version` не двигается. Повторный запуск безопасен.

## Ручные действия

Обычно это делается командами стража — `/retry НОМЕР` и `/resolved НОМЕР`.
Напрямую в базе, если стража нет под рукой:

```sql
UPDATE outbox SET state='pending', next_attempt_at=0, send_started_at=NULL WHERE id=<id>;
UPDATE outbox SET state='done', payload_json='{}' WHERE id=<id> AND state='ambiguous';
```

Почистить старое (после проверки):

```sql
DELETE FROM outbox WHERE state IN ('done','expired') AND updated_at < <ms>;
```

> Сервис лучше остановить. Одна запись в WAL из второго процесса не сломает
> базу, но результат будет неожиданным для работающего воркера.

## Резервное копирование

Ценного два: **база** и **MAX-сессия**, оба в `data_dir`.

```bash
systemctl stop telemax
cp -a data /backup/telemax-$(date +%F)
systemctl start telemax
```

На ходу — только так:

```bash
sqlite3 data/bridge.db ".backup /backup/bridge-$(date +%F).db"
```

`cp` работающей базы в режиме WAL даёт битый файл.

---

## Чего в логах нет и не будет

Токены, секреты сессии и полные телефонные номера не пишутся ни на одном
уровне логирования (`bridge/observability/`, тест `tests/test_redaction.py`).
Если такое встретилось в журнале — это баг, и его надо чинить, а не
обходить.
